五、顺序陷阱：账号报废
口诀：先负数刷钱，再买 FLAG

操作 ① 检查 ② 扣款 余额
初始 — — 1000
cost=2000&goods=2 通过 1000 - 2000 -1000
cost=-9999&goods=2 200 > -1000 → 拦截 执行不到 -1000
换商品 / 加大负数 真实价均 > 负数余额 执行不到 无法自救
为什么救不回来？
负数只作用于 ② 扣款，而 ① 检查永远先执行。 余额为负后，所有商品真实价都是正数，检查恒拦截 → 扣款代码永远不可达 → 该账号报废，只能换新用户名重新注册。

六、修复视角与总结

// [错误] 检查用真实价，扣款用客户端价 if ($real_price > $money) die('Money Not Enough.'); $money = $money - $cost; // cost 来自 $_GET，可控 → 负数加钱 // [正确] 全流程只信任服务端数据 $real_price = get_price_from_db($goods_id); // 价格实时查库 if ($real_price > $money) die('Money Not Enough.'); $money = $money - $real_price; // 扣款也用真实价
只传商品 ID
客户端不提交价格、数量等敏感数据
价格实时查库
校验与结算共用同一数据源
事务 + 原子更新
money = money - price 原子扣减，防并发
一句话总结
逻辑漏洞的内核：对同一个业务事实，校验与执行用了两个数据源。 凡是涉及金额、数量、权限的参数，永远让服务端说了算。
