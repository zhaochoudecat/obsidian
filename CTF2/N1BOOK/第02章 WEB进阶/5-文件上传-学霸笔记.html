先看环境：线索比 payload 更重要
入口 页面只有一个 multipart/form-data 文件上传表单；首页直接输出 show_source(__FILE__)，源码泄露成为最重要突破口。
GET 首页 → show_source → 拿到过滤逻辑 → 构造绕过
响应头 / 404 线索
前端：openresty　|　后端：Apache/2.4.7 + PHP/5.5.9
关键推断：后端使用 mod_php，需要重点考虑 Apache 的多后缀解析。
漏洞一：最后一个点决定“白名单后缀”
代码用 strrchr($name, '.') 找到最后一个点，再取其后的字符串。它只验证最后一段，没有验证完整文件名中是否出现过 .php。
1文件名：shell.php.jpg
2后缀提取：只看到 jpg → 通过白名单。
3真实文件名仍保留 .php 这一段。
4Apache 从右向左尝试处理器：.jpg 无处理器 → 继续识别 .php → 交给 mod_php。
记忆点：应用层只看最后一段，而 Apache 可能继续向左找可执行扩展；两套规则叠加才形成 RCE。
漏洞二：PclZip 解压目录穿越
ZIP 分支只拦截“以 .php 结尾”的条目，却没有检查条目名中的 ../。PclZip 2.8.2 解压时直接拼接目标路径，导致文件可写出临时目录。
条目名../../shell2.php.jpg：结尾是 jpg，不匹配 /\.php$/。
解压后upload/<md5>/../../shell2.php.jpg → 解析 .. → 写入 web 根目录。
清理范围check_dir() 只递归 upload/，根目录文件不会被这段逻辑删除。
利用路径：快解与预期解
A最快 直接上传 shell.php.jpg → 文件落在 upload/<md5>/ → 请求文件触发 Apache 多后缀解析。
B预期解 ZIP 条目使用 ../../shell2.php.jpg → PclZip 穿越到 web 根目录 → 同样依靠多后缀执行。

修复清单：把“文件名”和“执行权限”一起管住
1校验完整文件名：不仅检查 pathinfo() 的扩展名，还要拒绝任意位置出现的 .php。
2上传后随机重命名，例如 md5(uniqid()).jpg，不要让用户控制落盘文件名。
3解压前拒绝 ../、斜杠、反斜杠和绝对路径；或启用可靠的目录限制。
4上传目录关闭脚本执行权限；Apache 用 FilesMatch 精确限制 PHP 处理。
OK文件内容检查、文件名随机化、存储目录禁执行，三层防线缺一不可。
OK后端行为要与反向代理规则一起验证，避免“前端过滤通过、后端解释器执行”的错位。
